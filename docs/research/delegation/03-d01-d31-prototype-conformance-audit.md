# 03 · 「交代工作」D01–D31 原型设计符合性审查

**审查日期**：2026-11-16  
**原型基线**：Mira Cloud `dev` commit [`68a5dfc`](https://github.com/uichat-mira/mira-cloud/commit/68a5dfccf6974ff5370a28eccd5fff47efee1fa1)、已合并 [PR #108](https://github.com/uichat-mira/mira-cloud/pull/108)  
**对照权威**：[31 条正式产品决议](../../product/delegation-intelligent-ui.md)；[上一阶段原型实现与局限](./02-delegation-page-prototype.md)  
**范围**：已提交的独立 `/new` 原型、真实 json-render 控件绑定、组件交互、桌面/移动布局、历史和批注模型。**这是设计符合性审查，不是正式工作流或生产验收。**

## 结论

**可以继续沿用现有独立页面，但未达到 D01–D31 的完整原型覆盖，不建议宣称设计已收口。** 当前体验仍是「静态需求正文 + 单独的动态字段区 + 独立 Markdown 修改」；完整产品要求的是一份可共同编辑、批注、修订、版本化且始终一致的 Intelligent UI 工作文档。

按下述**原型可见交互**的保守分类，31 项中：**3 项具备雏形、11 项部分演示、17 项未在原型呈现**。这些数字不是正式业务实现率，更不是代码质量或后端交付比例。「缺失」只指原型缺少与决议对应的可体验路径；真实运行服务按当前原型阶段仍明确不在范围内。

## 需要优先处理的设计问题

### P0-1 自然语言入口和自适应需求（D02）

目前 `delegation-fixtures.ts` 声明三个预制任务、每个任务固定三阶段；`delegation-page.tsx` 仅允许切换这三种场景。用户无法从自己的意图进入，也无法看到 Mira 根据需求变化而组装不同结构。下轮应在**原型层**支持输入自然语言意图、切换/生成不同内容结构（可使用确定性的 Fixture 生成器；不强制接真实模型），而不是增加更多固定表单。

### P0-2 正文与组件一份需求真相（D09–D10）

`delegation-page.tsx` 正文来自 `scenario.text` 或局部 `editedBody`；动态字段通过 json-render `StateProvider` 独立管理，只有 `delegationSummary` 更新。即使控件改变了频率或其他规则，正文仍可保留相矛盾的描述，并且 `accept()` 只检查 `streaming`／`unresolved`／`historical`。

原型修订目标：同一份明确的数据快照派生正文核心语义与控件；其余自由编辑文本作为差异草稿标记；**未解决的语义矛盾必须阻止接受**。这可以先用确定性逻辑做，不应为此启动正式后端工程。

### P0-3 已接受阶段的编辑与版本存留（D07、D08、D29）

`accept()` 前进下一阶段时会 `setEditedBody(null)`；`reviewStage()` 回看历史也会这样重置。文字编辑没有按阶段/修订保存，导致原型里用户写过的正文在阶段转换后无法可靠回看。该问题比「没有云端自动保存」更紧迫，因为它阻断原型自己的用户旅程。

在**浏览器状态**中加入 per-stage `draft/revision/acceptedRevision` 即可验证历史只读、显式重开编辑、正式提交时后续接受失效；生产持久化仍留给技术验证。

### P1 批注从「列表」变成「随文审阅」（D03–06、D23–26）

当前只保存 `excerpt` 字符串与 `stage`，没有确定的原文 anchor / offset / 语义组件 id。右侧批注列表没有和对应文段对齐，也没有批注单击回到原文、Diff、批量确认和历史锚点。优先用 mock 文档 anchors + 对应组件语义 ID 完成视觉/交互原型，再研究 Milkdown/ProseMirror 精确锚定与持久化技术实现。

### P1 流式修订应展示有意义的变化（D30–31）

当前 `setInterval` 每 740ms 更改 `streamStep`，追加固定文本并调整局部 Note，之后把 open 批注标为 suggested。它只能证明「UI 会动」，不能证明用户看懂**正文哪里改了、控件怎么同步改变、半成品为何不能接受、中止后看哪一版**。建议使用同一组具有真实内容差异的预制 patch 事件演示，不接正式模型也能验证体验。

### P1 长期工作应在同一时间轴延续（D12–21）

最终阶段现在只显示「三个阶段已经完成演示验收」。至少要有**独立、完全标注为 Fixture**的后续里程碑、价值通知、暂停/恢复/提前结束、到期报告与在途取消反馈示例；不实施 Cloud Pi 调度或权限系统。否则「交代后持续负责」这一产品主旨在原型里完全不可见。

### P1 移动触控与面板位置

Chrome DevTools Protocol 在 390×844 模拟视口对真实已构建网页测得：`innerWidth=390`、`document.scrollWidth=390`，**无页面级水平溢出**。但部分实际控件高度：返回 30px、场景按钮 34px、流式修订 30px、接受阶段 40px；低于 [MiraDesign 的 44×44px 触控目标](../../../DESIGN.md)。顶部阶段展开 44px。移动底部批注面板、软键盘避让、焦点恢复和触屏选区仍缺真机证据。

## 原型审查与生产验证边界

原型阶段**不要求**建立 Cloud Auth、Task API、真实 Scheduler、Server persistence、真实模型推理、实际发送/支付或完整端到端 Agent 执行；这些仍由 [技术验证清单](../../product/delegation-technical-validation.md) 管理。

但不应以「还在原型阶段」掩盖**产品体验本身必需的行为**：自由输入、真正的同源数据、可回看的历史、批注位置、明确 Diff、流式中止、同一时间轴的长期工作续接。以上都可用可信 Fixture 表现并交由用户做设计验收。

## 下一步建议：三小轮，不重建 Playground

1. **设计回归 A（P0）**：意图输入与自适应阶段、统一文档模型、字段同步、浏览器态历史/重新验收，保障「用户看到并接受的是同一份约定」。
2. **设计回归 B（P1）**：Office 式文本/组件锚定批注、对应定位、可见差异、集中修订、批量确认和有意义的流式/中止演示。
3. **设计回归 C（P1）**：完成委托后的同一时间轴里程碑 Fixture、暂停/恢复/期限/成果视图，完成移动触控 44px、软键盘、滚动与面板的视觉验收。

每轮在已有 `/new` 上修，不另造并行入口；保留 MiraDesign 视觉规范、json-render 官方渲染器以及「Fixture 不等于真实运行」的边界。每轮都应有实际操作路径和浏览器/测试证据。

**审查方法和限制**：对照 PRD 全量条目、GitHub `dev` 源码、PR #108 的交付合同、仓库既有截图和 Mac 上本地/公开静态预览的 CDP 控件几何。未在此次逐一执行 31 条复杂业务场景；UI 端的截图与模拟浏览器几何不代表移动真机、真实模型或服务端权限验收。**本审查仅记录问题与建议，不修改 Workbench 运行时代码、不创建 Issue，也不自动改变 PRD 的产品决议。**
