# OMM 私人 Agent 与独立运行时：探索性讨论札记

**记录日期**：2026-11-18  
**状态**：未充分调研的讨论草案；**待进一步讨论、调研和验证**  
**效力**：仅记录近期产品意向、技术假设与证据缺口；**不是**新的架构基线、ADR、已批准技术选型、工程 Issue、实施或部署授权。

## 1. 讨论缘起与产品意向

近期讨论提出：

- **OMM / Oh My Mira!** 面向一位主人的私人持续智能体，而非面向不特定客户的多租户 SaaS。因而可重新审视为多租户服务设计的租户模型、租户间隔离和复杂权限投影，但**不代表**取消主人身份认证、设备安全、工作/记忆作用域隔离、外部工具授权及审计。
- **OMM 与 Cloud Pi（烤派，CP）是两个独立产品，不共用服务设施。** 不能默认共享 Agent 进程、Scheduler/Run、数据库、存储、配置/密钥或部署生命周期；CP 未来可能由另一位使用者单独使用。复用设计经验或经审查的开源代码，不等于复用 CP 的运行服务。
- 追求**轻量、快速、稳定、功能足够**。人格上下文、记忆和工具希望在可信边界内按需激活或选择，而不是开发者为每个场景写死完整流程。

以上是**用户表达的产品方向**，尚未转化为经过评审的完整技术规格；尤其没有证明某套架构能够低成本且稳定地实现。

## 2. 待验证的技术假设（不作选型决定）

1. **执行内核**：Pi SDK 是值得研究的候选；OMP 可能适合较重的编码/工程执行，但是否需要、如何接入均未决定。不得把「Pi + 某个自研 Resolver」写为已批准方案，也不以当前版本号决定架构。
2. **动态人格**：需区分稳定身份/角色承诺与随情境变化的表达；如何选择、恢复以及防止不当身份漂移仍待评估。
3. **记忆激活**：需区分长期事实、会话上下文、工作成果与候选记忆；检索方式、来源校验、纠错/删除、注入风险以及上下文成本均待研究。
4. **工具分配**：运行时可以动态挑选已获授权的工具，但不能动态创造权限；能力发现、调用前策略校验、审批、预算、取消和失败恢复的接口需要实验。
5. **运行与持久化**：OMM 需要自有工作生命周期和独立执行事实；是复用经验证的代码还是采用其他轻量组件尚无结论。不得照搬 CP 的部署或令 OMM 依赖其运行实例。
6. **认证和跨端**：单主人不意味着允许匿名访问。OMM 的身份与 Cloud Auth 如何衔接、与 CP「不共用服务设施」具体包含哪些身份基础设施、Desktop/Mobile 的工作交接边界，均需专题讨论；不可自行假定例外或直接取消认证。

## 4. 缺少的研究证据与讨论议题

- 相同真实场景下的首响应延迟、模型调用次数与 Token 成本、CPU/RSS、常驻空闲占用。
- 普通对话、跨会话记忆、动态工具选择的质量；与静态最小方案进行可重复对比，避免无收益的额外路由模型调用。
- Session/Run 重启恢复、幂等与取消、并发、错误传播、长任务到期报告和 Artifact 来源链。
- 私人身份/设备验证、公开 IM 与私有记忆隔离、外部写操作审批、密钥安全和撤权语义。
- OMM 与 CP 现有代码资产可复用的边界、兼容性、维护成本和迁移计划；独立部署的故障域及最小资源需求。
- RP/Cordis/OMP/Pi 生态相关方案，是否确有必要引入，需基于具体能力缺口与许可证/维护成本调查。
