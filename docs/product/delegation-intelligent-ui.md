# Mira Cloud「交代工作」——智能长期工作交互 PRD

**版本**：v1.0（31 项用户决议整理稿）  
**日期**：2026-11-14  
**状态**：31 项产品决议已确认，作为「交代工作」的设计基线；技术可行性与视觉体验待验证，功能尚未实现  
**适用范围**：Mira Cloud 的长期定时／条件触发工作，不是 Mira Desktop 的即时施工任务。

## 1. 产品定义

用户不再通过聊天框或传统表单“填写委托”。Mira 根据用户意图主动生成**需求正文与可操作的动态确认 UI**；用户像审阅 Office 文档一样选中、批注、修改，Mira 根据一轮集中反馈重写，用户逐阶段明确接受。委托成立后，**同一条主时间轴**延续为长期工作监测、决策与成果交付界面。

**核心交互**：单主线时间轴 × Intelligent UI 动态画布 × 锚定式批注 × 显式阶段验收。  
**核心责任**：定期检查不等于定期通知；发现重点才打扰；有期限必须在期限内诚实报告。

## 2. 用户价值与设计原则

- **先交作品，不先盘问**：AI 尽可能形成可审阅初稿；有可靠上下文则直接起稿，无上下文时允许极简自然语言输入。
- **只有一条主线**：不做用户可见的树状分支、流程图或并排路径。阶段内可以多轮修订；执行记录在相关里程碑下按需查看。
- **AI 负责整理，用户负责验收**：逐阶段明确接受；AI 不能替用户按下确认。
- **文档是主角**：默认让需求画布占据主要空间；批注按需出现，避免对话流替代文档审阅。
- **动态但可信**：文字、结构化字段和确认 UI 在阶段接受前一致；生成中不开放阶段验收。
- **托管不是即时执行**：「接受并交代」是委托提交与最终验收，不承诺立即运行或即时完成。

## 3. 用户旅程与交互合同

### 3.1 意图进入

无明确上下文：以简洁输入表达目标。已有可验证上下文：Mira 自动形成初稿。二者都进入同一需求画布，而非聊天消息流。

### 3.2 单主线需求审阅

1. Mira 生成当前阶段的需求描述与相关确认 UI；阶段数量和内容按工作情境决定，不固定成四步表单。
2. 用户可直接修改日期、选项、数值等结构化字段；修改自动保存为草稿。
3. 用户框选文字后出现轻量批注入口，主动点击才打开右侧批注栏；同时支持全文批注。组件级批注属于技术验证项。
4. 批注可以积累多条，点击「提交修订」后 AI 一次综合处理。修改时**流式更新**正文及动态 UI；期间允许阅读、滚动、中止，不允许同时编辑。
5. 新版以当前内容为主，轻量显示修改情况；旧批注保留原版本锚点，展示处理结果、可回看原文与差异。
6. 批注须经用户确认解决或主动放弃才算闭环；可批量确认 AI 已提出解决方案的条目，但不能混入未解决条目。
7. 只有在批注闭环、生成完成、正文与结构化字段一致时，才能点击「接受需求」进入下一阶段。

### 3.3 回溯与历史

已接受阶段默认只读；明确点击「修改本阶段」才进入编辑。修改草稿不立即推翻历史接受；**正式提交修改后**该阶段及之后阶段的验收全部失效，必须沿原主线依次重新确认。保留历史版本，不创建新分支。

### 3.4 最终委托

最后阶段显示工作目标、周期、条件、期限、交付要求、授权与费用／外部副作用范围。点击**「接受并交代」**同时完成最终验收与委托提交。请求接收、运行开始、结果生成、通知投递必须展示不同的真实状态。不能因按钮点击就宣称工作已经运行。

### 3.5 长期托管

- **执行频率**：定时检查最密每小时 1 次；可按更低频率运行。
- **通知触发**：无符合关注条件的重点结果，不发送例行打扰；符合条件则提示并提供相关成果。
- **到期责任**：有明确期限的工作，在期限内输出诚实最终报告，包括发现、证据、实际覆盖、未完成内容与缺口；到期停止新触发，历史保留。
- **暂停／恢复**：暂停停止新的定时触发；恢复不补跑；暂停不顺延截止期限，到期仍有最终报告义务并说明暂停造成的缺口。
- **主动提前结束**：停止后续触发，尝试取消在途执行；展示取消请求和最终真实状态，历史及已有成果保留。结案摘要按需生成，不强制最终报告。
- **运行中改规则**：用户确认后，新规则只用于后续执行；已开始的执行继续沿用原版本，不自动重跑。
- **用户介入**：需要额外授权的动作局部阻塞，其他独立执行和定时计划保持有效；安全无法继续的本轮执行可停止，但不得无故暂停整项工作。

### 3.6 同一时间轴持续演变

需求确认 → 委托已接收 → 持续托管 → 重要工作里程碑／待用户决定 → 成果／到期报告，沿**同一条主时间轴**呈现。主线展示有意义的进展，工具调用、日志、每次 Run 的细节收进节点内部。需求阶段靠用户接受推进，运行阶段依权威事件和用户许可推进。

## 4. 界面与响应式

**桌面**：左侧单主时间轴；中间可阅读／可操作的动态需求画布；右侧 Office 式批注栏按需展开。正文锚点与右侧批注尽量纵向对应，支持双向定位、滚动跟随、密集卡片避让和折叠。普通文字选中不强行弹出侧栏。

**移动端**：顶部紧凑阶段进度；完整时间轴按需展开。画布优先占屏；批注从底部面板展开，保留原文上下文，关闭后恢复阅读位置。触屏选区、软键盘、Safe Area、滚动定位另行验证。

视觉资产沿用 MiraDesign 的 Cloud Web 基础；不新造第二套视觉 Token。组件和流程语义动态生成，但授权、接受、取消、保存状态不允许随意改变含义。

## 5. 状态与数据不变量

- **交代草稿**、**批注草稿**、**已提交修订**、**已接受阶段**、**委托请求**、**真实执行**是不同状态。
- 自动保存正文、未提交批注、阶段进度与版本；保存失败必须明确告知，不可假装保存成功。
- 流式生成可以分片展示，但部分内容不得被误认为已校验正式版本；中止或失败保留原稿、用户批注和历史，不将半成品标为可接受。
- 批注锚定原版本和语义对象；不强制自动迁移到新版。仅当用户明确认可或放弃才闭环。
- 执行数据与通知数据均以权威系统回执为准；不以 UI 推断已开始、已完成、已取消或已投递。
- 同一工作可以有多个执行记录和多个成果，但用户可见的主工作时间轴只有一条。

## 6. 一期范围与非目标

**一期应提供**：自适应意图进入、单主时间轴、可审阅动态需求、文字与全文批注、集中修订、流式展示、逐阶段接受、自动保存、历史版本、已接受阶段回溯、长期工作配置与状态、按价值通知及到期报告合同、桌面／移动响应式。

**有条件纳入**：组件级锚定批注（D03）、动态组件 Diff（D05）。必须通过最小技术验证，不能以静态示意充当验收。

**明确不做**：聊天框主导的委托、多主分支／树形编排、桌面式即时工作执行、AI 自动接受、流式期间双向并发编辑、AI 自动迁移旧批注锚点、智能判定哪些后续历史阶段免重新验收。

## 7. 产品验收标准

1. 一项示例长期监测能从一句意图形成初稿，经 3 条批注、1 次集中修订和显式接受，完成整个委托流程。
2. 文本及结构化字段修改经自动保存和同步后形成一致的最终需求；冲突时禁止接受。
3. 生成中用户能看到实时变化；可中止且不损坏原稿和已提交批注；生成完成后才能编辑或接受。
4. 未闭环批注阻止验收；批量确认仅作用于用户选择且 AI 已提出解决方案的条目。
5. 历史节点默认只读；提交历史阶段修改后所有后续阶段需重新验收。
6. 桌面批注双向定位、移动端底部批注与选区交互满足基本可用性，无错误锚定或丢失草稿。
7. 托管配置允许最密每小时检查一次、重要结果才通知、可选截止期限。期限报告、暂停和结束行为符合约定。
8. 所有执行与提交状态依真实来源而非演示假数据。验证过程中使用 Fixture 时必须显式标注。
